A. Deliverable flaws — the dpo_tune deliverable (7)

Defects in what the org actually produced — is it a real, usable, distributable artifact?

1Two different PreferenceDataset classes ship in one packageDUP-DATASET
public.py defines PreferenceDataset that takes (prompt, chosen, rejected) tuples and yields PairBatch. dataset.py defines a SECOND PreferenceDataset that takes PreferenceExample objects and yields PreferenceBatch with differently-named fields (chosens/rejecteds vs chosen/rejected). dataset.py's own docstring admits it: “This module intentionally provides a different PreferenceDataset than dpo_tune.public.PreferenceDataset… kept for backwards compatibility with earlier exercises.” __init__ re-exports the public one as PreferenceDataset plus the dataset one's PreferenceExample/PreferenceBatch — so a user gets two incompatible batch shapes from a single import.
2TrainerConfig (the one with the real hyperparameters) is exported but never usedDEAD-CONFIG
config.py defines TrainerConfig(beta, lr, batch_size, epochs, seed, ref_kl_coeff) — the real DPO knobs. But the actual Trainer (public.py) takes a DIFFERENT DPOConfig(seed, batch_size, shuffle, epochs) that has no beta, no lr, no ref_kl_coeff. The Trainer hard-codes beta=0.1 as a separate kwarg and never reads TrainerConfig. So lr and ref_kl_coeff are accepted by the public config type and silently ignored — dead configuration.
3The dedicated loss.py is orphaned — Trainer.fit re-implements the loss inlineORPHAN-LOSS
A whole task (“Add a new DPO loss implementation”) produced dpo_tune/loss.py with a proper dpo_loss(): the beta DPO term plus a symmetric KL proxy, with both torch and pure-scalar paths. But Trainer.fit() in public.py computes the loss inline as math.log1p(math.exp(-advantage)) and never imports loss.py. grep confirms loss.py is referenced nowhere in the package — only by its own test_loss.py. Two independent DPO-loss implementations; the polished one is unreachable.
4The brief's required reference-model KL term never reaches trainingKL-UNREACHABLE
The brief demanded “a reference-model KL term.” loss.py HAS a kl_weight proxy — but that's the orphaned module. The wired Trainer only computes the implicit-KL DPO term (beta*(pol_diff − ref_diff)) and exposes no KL coefficient at all (ref_kl_coeff lives on the dead TrainerConfig). The explicit KL knob the brief asked for exists in the repo but is unreachable through the public Trainer.
5pyproject.toml is a ruff config, not packagingPKG
98 bytes: only [tool.ruff] and [tool.ruff.lint]. No [project] table (no name, version, dependencies), no [build-system]. `pip install .` fails — there is nothing to build. The “Python library” is not installable or distributable.
6README is still the seed stubREADME
README.md is 15 bytes: “# company repo”. No install, no usage, no DPO explanation.
7Stray + leaked files in the deliverableSTRAY
Root test_smoke.py (`assert True`) sits outside tests/. 20 harness-internal files leaked into the repo (docs/evals/*.json, docs/exec-plans/*.json/.md), plus a committed 0-byte lock file docs/exec-plans/tech-debt-tracker.md.lock.
