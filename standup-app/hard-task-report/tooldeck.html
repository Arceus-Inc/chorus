A. Deliverable flaws — the tooldeck deliverable (7)

Defects in what the org actually produced — is it a real, usable, distributable artifact?

1Two complete, rival ToolRegistry implementations with incompatible APIsDUP-REGISTRY
tooldeck/registry.py defines ToolRegistry with register(func, name=None) and dispatch(name, args_dict). root tool_registry.py defines a SECOND ToolRegistry with register(name, func) — the arguments are REVERSED — and dispatch(name, *args, **kwargs). Same class name, two files, two incompatible call conventions. Whichever one a caller reaches, code written for the other breaks.
2Two incompatible `tool` decoratorsDUP-DECORATOR
tooldeck/registry.py exposes a keyword-only `tool(*, name=None)` — you must write @tool(name="x"). root tool_registry.py exposes a positional `tool(name)` — you must write @tool("x"). The two are mutually exclusive: @tool("x") TypeErrors against the package, @tool(name="x") fails the root's required positional. A user's code breaks depending purely on which module they imported.
3The error types are each defined twiceDUP-EXCEPTIONS
UnknownToolError and ToolExecutionError are defined in BOTH tooldeck/registry.py and root tool_registry.py — distinct classes despite identical names. `except tooldeck.UnknownToolError` will not catch the root module's UnknownToolError. ToolCallMalformedError / ToolArgumentValidationError are likewise duplicated across tooldeck/validation.py and root tool_registry.py.
4The green test suite imports from both universes at onceTEST-ILLUSION
The tests do `from tooldeck import ToolRegistry, tool, …` AND `from tool_registry import ToolArgumentValidationError, ToolCallMalformedError, …` AND `from tooldeck.schema import schema_for`. They co-pass only because pytest puts the repo root on sys.path so the root tool_registry.py is importable. `pip install tooldeck` ships only the package — the root module and the tests that import it break, and the package never sees the rival. This is GRPO's exact illusion.
5The retry-or-error dispatch is duplicated, and the root copy is a stubROOT-RETRY-HACK
The brief's retry/validate dispatch exists twice: tooldeck/call.py::dispatch_tool_call + tooldeck/validation.py (the real path) AND root tool_registry.py::dispatch_tool_call_with_retry. The root copy is shaped to the tests, not the brief: it hardcodes `if tool_name == "echo": …` as its 'validation' instead of using the schema. So the headline feature is split between a real package half and a test-fitted root hack.
6No packaging, and the rival lives outside the packagePKG
No pyproject.toml / setup.py. tool_registry.py sits at the repo root, outside the importable tooldeck/ package entirely — so even if the package were installed, the root rival (and the tests that need it) would be left behind. Not distributable.
7Stray root tests + README stub + leaked harness filesSTRAY
Three test files sit at the repo root outside tests/ (test_smoke.py with `assert True`, test_schema.py, test_tool_registry.py). README.md is the 15-byte '# company repo' stub. ~24 harness-internal files leaked (docs/evals/*.json, docs/exec-plans/*).
