chorus · employee design · deep archetype

Backend Engineer
the engineer who ships a service a stranger can depend on — and proves it.

Where the Designer ships an experience, the Frontend Engineer an interface, the PM a decision, the Backend Engineer ships a running service — the API, the data model, the migration, the queue a real system leans its weight on. An LLM will confidently declare a service done — green unit tests, a tidy self-check — while the endpoint 500s under load, the migration locks the table for four minutes, the query is quietly N+1, and a broken object-level check lets anyone read anyone's data. So the Backend Engineer's one failure mode that matters is the unproven, unsafe, unmigratable service that passes its own tests. The entire design is built around one inversion the whole field converged on: "it was tested" must be a file on disk, not a claim in the transcript — a durable test_evidence bundle, graded against tests the agent cannot see or edit, against a real database, under load, with the security scan clean. Not trust. Proof.

01 — The thesis

Depth is a loop, and the blast radius is a service in production.

chorus's employee is deliberately thin and stateless — "a replayable identity, not a process." The Backend Engineer keeps that invariant. It gets "deep" not by holding state, but by composing durable things into a proven, operable service:

  • A service it owns — an endpoint, a data model, a migration, a worker — and the contract, dependencies, and reliability budget it all has to satisfy.
  • A durable evidence bundle — the tests it ran against a real DB, the contract it verified, the load percentiles it hit, the migration it rolled back and forward — accruing on disk, not in the transcript.
  • A verification swarm — author the tests, drive the running service, red-team the diff — all in one beat, before anything lands.
  • An open worktree — the code, the running dependencies, the migrations of a service in progress.

What makes it work — the industry-converged discipline, encoded structurally:

newEvidence as an artifact

A machine-readable test_evidence/ bundle the beat emits: JUnit + coverage, contract verification, migration round-trip, load percentiles, mutation score, a11y of the API surface. The DoD greps manifest.json — "it was tested" is a file, not a sentence (§10).

newReal deps + held-out grader

Integration tests run against a real Postgres/Redis/Kafka (Testcontainers, not H2/mocks); the grader's tests are hidden and read-only, so the agent cannot pass by editing them. SWE-bench's FAIL→PASS + PASS→PASS, in one beat.

newUnrestricted, but confined

Full freedom to install, migrate, run, and load-test — inside a box with a registry-only egress allowlist and secrets stripped before the autonomous phase. Safe by confining the environment, not by narrowing the tools.

The crux — what it's governed against

The Designer is governed against shipping beautiful, broken UI; the Analyst against being confidently wrong; the PM against deciding without evidence. The Backend Engineer is governed against the plausible service that passes its own tests and fails in production — the endpoint that 500s under load, the schema change that locks the table, the N+1 that melts the DB, the missing authorization check that leaks data. An LLM will report all-green while every one of these hides below the unit-test line, because it wrote both the code and the tests. So its governance is proof-class: real-dependency tests, a durable evidence bundle graded outside the agent's claims, percentile SLOs as hard gates, and a mutation score that proves the tests would actually catch a bug. That single inversion — proven, safe, and operable is structural, not hoped-for — shapes its DoD, its tools, and its authority.

Field context — self-verification is not enough, and the field knows it
The evidence is blunt. On SWE-bench Verified, ~88% of agent trajectories self-verify — yet 35.7% of those still ship an incorrect patch. Reward-hacking is documented and routine: RL-trained agents "overwrite unit tests, monkey-patch scoring functions, delete assertions, or prematurely terminate" to turn a suite green; a trajectory-monitor plus a quality judge drops the hacked-resolved rate from 28.57%→0.56%. And benchmark scores overstate reality — SWE-bench exists precisely because it grades a patch in a clean container against hidden, held-out tests it applies as a git diff, checking FAIL→PASS and PASS→PASS. The convergent verdict: never accept the agent's own "done" — verify it against a real system, with tests it cannot touch.

02 — Identity & the role triple

Bex — Backend Engineer.

It owns a service, not a screen or a question: "add the idempotent payments endpoint," "migrate orders to the new schema, zero-downtime," "stand up the webhook ingest worker." The stack — language, framework, datastore — is discovered, not assumed and never hardcoded: it reads the repo, detects Go+Postgres or Python+Mongo or Node+Redis or Java+MySQL, and binds to that ecosystem's real tools. Swap one stack for another and the loop, the DoD, and the shape of the evidence are identical — only the discovered tool bindings change (§03). In chorus a role is exactly three things:

The Backend Engineer is the Engineer's structural twin — and the Frontend Engineer's mirror

The parallel is exact, so almost nothing is invented: it reuses the Engineer's brief · harness · dod · lander plugin shape, its UNRESTRICTED sandbox, and its reviewed_build DoD. What it adds is the Frontend Engineer's move, pointed at the server: design-lint → test_evidence (a durable, machine-readable proof bundle); the UI-Tester → an API-Verifier that drives the running service; the Frontend's Playwright browser → a real database + a load generator. Where the Frontend proves behaviour in a browser, the Backend proves it against a real datastore, under load, across a migration. Reuse over invention — the point of a role-agnostic kernel.

The principles it runs on

I

The user's reliability is the spec.

Their traffic spikes, their network drops, their data is messier than your fixtures. You build for that, not the happy path on your laptop. Resilience is the job, not a nice-to-have.

II

Correctness is measured against the states that occur.

Most defects are state defects — impossible states, races, stale data. Make illegal states unrepresentable; keep one source of truth. Fewer sources of truth, fewer lies in the database.

III

Green unit tests are necessary, never sufficient.

Real behaviour lives against a real datastore, under real load, across a real migration — so that's where it gets proven. A suite that only passes on mocks proves the mocks.

IV

The service must survive failure.

The dependency will time out, the queue will back up, the row will be locked. Every path owns its timeout, retry-with-jitter, and fallback. At-least-once is the default; make consumers idempotent.

V

Security is a gate, not a feature.

Broken object-level authorization is the #1 API risk. Validate at the boundary, authorize every object, parameterize every query, never hardcode a secret. An endpoint that leaks is a broken endpoint.

VI

You build it, you run it.

The migration must apply while the old code still runs; the service must expose its health, its metrics, its traces. Operability ships with the change — it is not a later ticket.

03 — The surface of work

A ticket in; a proven, operable service out.

What the service is grounded in

A backend engineer doesn't build from the prompt; it builds from the contract and the system it lives in. Both are first-class context the loop reads before it writes a line:

new① The contract + data model

The API contract (OpenAPI / gRPC / GraphQL schema), the data model + its integrity constraints, and the acceptance criteria. Grounds "what shape must this endpoint be, what invariants must the data hold, and what does done mean." The API contract is to the Backend Engineer what DESIGN.md is to the Designer.

new② The running system

What exists today: the codebase (how services are actually built), the dependencies (DB, cache, queue) it must talk to, the migrations already applied, and the reliability budget (SLOs) it must not breach. Grounds "what can this actually integrate with, and what mustn't it break."

Stack-agnostic — the stack is discovered, not assumed

The Backend Engineer is not a Django engineer or a Spring engineer. It is framework-, language-, and datastore-agnostic: the same role builds Go+Postgres, Python+FastAPI+Mongo, Node+Nest+Redis, Java+Spring+MySQL, or Rust+Axum. Nothing about a specific framework is baked into the brief, the DoD, or the tools — because the first thing every beat does is probe the repo to learn the stack, then bind to that ecosystem's real commands and libraries. This is the field-standard pattern: Codex reads an AGENTS.md for the project's test/lint commands, Anthropic's harness reads an init.sh to bring the service up. Bex does the same.

readThe project probe — how it detects the stack

It reads the manifest + lockfiles (go.mod, package.json, pyproject.toml, pom.xml/build.gradle, Cargo.toml, Gemfile) to fix the language + framework; the docker-compose.yml to see which datastores it must talk to; and the Makefile / CI config / AGENTS.md for the actual build, test, migrate, and run commands. It never guesses pytest on a Go repo.

backendDiscovered commands, not hardcoded ones

test_evidence runs the commands the probe found, and the skills are ecosystem-agnostic principles (idempotency, expand-contract, contract testing) whose per-stack tool binding is resolved at runtime. The loop is invariant; the bindings are data. Add a new language and no role code changes — only its command map.

Worked example — hand it Go + Postgres

Bex reads go.mod (→ Go) and a postgres service in docker-compose.yml (→ the datastore), discovers go test ./… and golang-migrate from the Makefile, brings up a real Postgres via testcontainers-go, applies the migration up and down for the round-trip, drives the endpoint with k6 against its p95/p99 budget, runs Schemathesis off the OpenAPI spec, and emits the same test_evidence/ bundle. Hand it Django+Mongo instead and only the bindings change — pytest, testcontainers-python, Alembic, a Mongo container — while the beat, the DoD's six truths, and the evidence shape are byte-for-byte the same role. That invariance is the design.

Cold start — when there's no repo to probe yet

The probe assumes a repo exists. A greenfield service has nothing to detect — no go.mod, no compose file, no Makefile. So the stack stops being a discovery and becomes a decision, and hand-rolling a project from a blank main is exactly the kind of blank-page task an LLM does worst. Two moves close it — the direct analog of the Designer seeding a fresh product's DESIGN.md from a proven system rather than authoring tokens from nothing:

new① Decide the stack — with reasons

Map the task's real needs to a stack: consistency + transactions → a relational store; latency / throughput → Go or Rust; ML-adjacent → Python; a JS shop's BFF → Node. Weigh it against what the org already runs (a new service in a Python house is Python) and prefer boring, proven, and consistent over novel. Name the choice and justify it in one line — "Go + Postgres: low-latency, strongly-consistent transactional service" — the way the Designer names its house-style exemplar.

new② Scaffold from a proven starter, not a blank file

Fork a battle-tested skeleton (the project's own search-for-skeleton-projects reuse discipline) — a real layout with the framework, the migration tool, the test runner, and a docker-compose already wired — then diverge. Fork-not-invent: clone the closest proven structure and iterate within it, exactly the discipline the awesome-design-md library gives the Designer.

The cold-start beat bootstraps its own discoverability

Having decided and scaffolded, the beat writes the very surface future beats will probe: the lockfile, the Makefile / task runner, the docker-compose.yml with its datastores, and an AGENTS.md recording the build / test / migrate / run commands. So the first beat is a stack-choosing greenfield beat; every beat after it is an ordinary brownfield probe-detect-bind beat — the role converges to its invariant loop after one bootstrap. Governance rides on §12/§13: choosing a stack within the org's existing conventions is the engineer's call, but introducing a new language or framework to the org is precedent-setting and escalates — a one-line "this org has no Go service; here are two on-convention options" beats a confident, lonely new toolchain.

What it produces

The deliverable is a PR an engineer or a reviewer can trust — because the proof ships attached:

The service — a reviewed PR

The implementation: the endpoint/worker/migration, wired to the real dependencies, with its tests, its migration up/down scripts, and its observability (health, metrics, traces). Smallest change, on-contract, edit over add.

The evidence — test_evidence/

The durable bundle that makes the PR trustworthy: results against a real DB, contract verification, migration round-trip, load percentiles, mutation score, security scan — indexed by a manifest.json the DoD reads. Not a claim; a directory.

Composable — the Backend Engineer doesn't own the whole stack

It reads the contract, reads the code (feasibility), and takes the PM's decision and the Designer's / Frontend's surface as givens — it doesn't decide what to build, own the schema of record, or merge to production. It builds the service to the contract and hands a proven PR to review. Every claim of "it works" resolves to a file in the evidence bundle, so "done" is checkable, not asserted.

04 — Two modes — IC and under a manager

A single service, or a system it keeps reliable.

IC · one service, one beat

A human, a PM, or a manager assigns a ticket; the Backend Engineer runs one beat — read contract → implement → install & run → prove-in-beat → self-review — and lands the PR. The chorus tick/chat path: a role-faithful, DoD-gated beat. the default path

Operator · under a manager

On a team it also keeps the system honest: an incoming change is built to the SLOs and the migration discipline, and reliability drift (a slipping p99, a shrinking error budget, a stale dependency) is flagged back — the backend equivalent of the Designer's system-drift scan (§14).

The invariant both modes keep

The employee is stateless across services — continuity is the contract + the evidence + the decision base + the task rows, never a long-lived Bex. A multi-step build (schema → backfill → cutover) may span more than one beat; each rehydrates the worktree and the migration state where the last left off, from durable in-workspace state (git + progress + task list), not the context window.

05 — The beat: one loop, one landed PR

Read → implement → install & run → prove → self-review → land + evidence.

A backend beat is self-contained: it reads the contract, implements, gets the code running against real dependencies, and proves it in the same beat before it converges. Nothing is deferred to a later beat or a human — the proof ships with the change. Every node is a chorus object; the employee is stateless across the whole loop.

Two signature nodes. The teal one is the floor: proof is a gate on a real system, not a self-check — the test_evidence gates fail on a red test against a real DB, a breached p99, a dirty security scan, or a migration that won't roll back, and route back to fix (the dashed edge). The dark-red one is the reach: landing is a gate, not an action — the beat opens a reviewable PR and never auto-merges, the universal boundary across Devin, GitHub Copilot's coding agent, and Factory's Code Droid. Where the Frontend's signature is exercise the UI in a real browser, then open the PR, Bex's is prove it against a real datastore under load, then open the PR.

01Read

Ingest the contract, data model, acceptance criteria, and the codebase. Understand the invariants before touching a line.

02Implement

Write to the contract + tokens of the stack; smallest change; edit over add; make illegal states unrepresentable.

03Install & run

Install deps, apply migrations, bring up real dependencies (docker-compose, health-gated), start the service.

04Prove

Static + unit + integration-on-real-DB + contract + migration round-trip + load/SLO + mutation + smoke — authored and run now, into test_evidence/.

05Self-review

Adversarial diff review + API-Verifier verdict; fix, re-run until green — against the real system, not the mocks.

06Land + evidence

Open the PR; the durable evidence bundle lands with it. No autonomous merge — a human reviews.

06 — The subagents under it

Author the tests, drive the running service, red-team the diff.

Mid-beat, the Backend Engineer dispatches Tier-1 specialists (dream's spawn_subagent), each capability-minimized to a subset of Bex's toolset, each returning a typed, runtime-validated verdict — a direct lift of the Frontend Engineer's swarm onto the server substrate.

backendTest-Author

writes tests · never ships

Given the diff + acceptance criteria, drafts and extends the tests so they land in the same beat — Honeycomb-shaped: integration-heavy against a real DB, a thin e2e/contract layer, unit for the logic that isn't visible at the boundary. Writes tests, never production code.

tools: read_file · write_file · run_command · skill

backendAPI-Verifier

drives the running service · typed verdict

The Frontend UI-Tester's analog. Drives the running service against the acceptance criteria: property + contract tests (Schemathesis vs OpenAPI, Pact replay), hits real endpoints, captures latency percentiles + error rate + health, and returns a decisive ApiTestVerdict (pass/fail + findings + evidence paths).

tools: run_command · http_request · read_file · test_evidence

backendCode-Reviewer

read-only · adversarial

Read-only reviewer of the diff: correctness, that new behaviour has a test, no regression, on-contract, and the security pass — BOLA/IDOR, injection, secrets, and migration backward-compatibility. Returns PASS/FAIL; the engineer keeps ownership of the fixes.

tools: read_file · git (read) · test_evidence (read)

sharedWeb-Research Orchestrator

read-only · web + docs

The company-wide research subagent (declared once in src/swarm/): answers a framework / library / API question from the live web and returns cited, runtime-validated findings — re-pointed at backend docs and library behaviour (depth-2, as the Marketer's Strategist).

tools: web_search · web_extract

The validation sandwich — proof is enforced inside the beat

Correctness isn't gated by a single stochastic reviewer re-reading the code. It's enforced where the code is made: the Test-Author lands the tests, the API-Verifier drives the running service, the Code-Reviewer red-teams the diff — and the DoD's deterministic evidence floor (§09) is the out-of-beat backstop that greps for the bundle. Pre (design to the contract), live (run against real deps), post (Verifier + Reviewer) — the same three-layer sandwich the Designer uses for fidelity, pointed at a running system.

07 — Integrations (MCP & the running system)

Read the whole system; run real deps in a box; ship only through a gate.

An integration = (name, kind, capability, auth secret-ref, trust scope) — auth bound to a secret ref (ref:…), never inline; most are MCP servers. Where the Marketer's writable surfaces are channels and budget, the Backend Engineer's are a running system: datastores it must talk to, a container runtime that stands up real dependencies, a git host it opens a PR against, and an observability stack it reads its SLOs from. Every one is graded and gated on the same chorus trust layer the Marketer's go-live uses — and the grades sort exactly as the field's agent sandboxes do: registries + telemetry read-only; ephemeral deps run-in-a-box; PR / migration / deploy the highest gate.

Already built — the leash is not hypothetical

The grading reuses the WebPlugin trust layer chorus already ships: Capability{read · write_reversible · send · spend} with .gated, secret-ref binding, and a fail-closed __post_init__. The Backend Engineer maps onto it cleanly — read = telemetry / registries / docs; write_reversible = its worktree + an ephemeral Testcontainers datastore it can throw away; send = the one irreversible outward act (open a PR, apply a prod migration, deploy), which is gated fail-closed. Two field-standard reinforcements ride on top: the two-phase network (setup online behind a registry-only egress allowlist → run/test offline) and secrets injected per-session, stripped before the autonomous phase. The credential leash — the grant↔employee binding that denies an unbound employee — is the trust boundary made physical.

The datastore + container MCP — the live-connect layer, in depth

One integration cluster deserves its own treatment, because it is the single mechanism that turns "it works" from a hope into a fact at build time — Bex's exact analog of the Designer's Figma-MCP live-connect layer. The rule the whole field converged on: bring up the real dependencies, health-gate them, then test against them. A change that only passes against fakes has proven the fakes.

runReal dependencies (Testcontainers)

Spins up the same service type as production — Postgres, Redis, Kafka — in a throwaway container, runs integration tests against it, and destroys it whether tests pass or fail (the Ryuk reaper). Kills the "passes on in-memory H2, fails on prod Postgres" anti-pattern; containers.log in the evidence bundle proves a real DB was used.

runHealth-gated startup

docker-compose depends_on: condition: service_healthy + --wait + pg_isready — provision DB → wait healthy → migrate → hand the app the connection string. After starting the service, poll its health endpoint before declaring ready, never sleep.

runHit the running API

http_request against the live service the beat started — the server-side of "test as a real client would." Contract + property tests (Schemathesis, Pact replay) run against the actual endpoint, not a handler in isolation.

runLoad generator

k6 / Gatling / Locust drives traffic; percentile thresholds (p95/p99 + error-rate) are pass/fail gates that exit non-zero on breach — the SLO becomes a build gate, not a dashboard screenshot.

How it wires into chorus — a run-scoped MCP cluster on Bex's shelf

The datastore + container MCPs are declared on the manifest (mcp=("docker","postgres",…)), allowlisted, and scoped run · ephemeral: they stand up real dependencies inside the confined worktree and tear them down each beat — never touching a production system of record. They are the live feeders for the whole loop: the Test-Author writes tests against the real schema, the API-Verifier drives the running service + real deps, and the SLO watch reads the telemetry integration. Combined with the git host on the gated write side, they close the build-and-prove circuit end to end: run the real system in, hand a proven PR out. It is Bex's exact analog of the Designer's read-only Figma seam — except the system of record is a running datastore, so its bridge is run, not merely read.

The sandbox — unrestricted, but confined

Backend work requires arbitrary command execution: install packages, run builds, apply migrations, start servers, drive load. The field's answer is not to narrow the tools but to confine the environment. Anthropic states it directly: sandboxing enables autonomy — "by defining set boundaries within which Claude can work freely, they increase security and agency," and it "safely reduces permission prompts by 84%."

runTwo-phase network

The Codex model: a setup phase online for installs/migrations behind a registry-only egress allowlist (npm/PyPI/GitHub), then a run/test phase default-offline. The threat it closes: a compromised dependency has "seconds to read credentials" during install — the allowlist breaks the exfiltration step.

runFilesystem + secrets

Filesystem confined to the worktree; run as non-root; secrets injected per-session and stripped before the autonomous phase (Devin/Codex both do this). Both boundaries mandatory: without net isolation the agent exfiltrates SSH keys, without FS isolation it escapes the sandbox.

runBroad, powerful, few tools

A PL/shell action space (bash + file-edit + git) plus a few task-consolidated verbs (apply_migrations, run_tests) beats a fat catalog of one-tool-per-operation — the OpenHands / Anthropic tool-design consensus.

runDurable in-workspace state

Across a multi-beat build, state lives in the workspace — git history + a progress file + a task list — not the context window; install is a separately-timed phase (slow); compaction at phase boundaries. Anthropic's long-running-agent pattern.

How it wires into chorus — the Engineer's sandbox, one tier hotter

The manifest declares sandbox = UNRESTRICTED + net-allowlist (§08): the same trust tier the Engineer already runs, plus an egress allowlist for package registries and the dev dependencies. Credential guard, command deny-list, and worktree confinement still apply — landing UI to prod, or money-moving, is still gated. It is Bex's exact analog of the Designer's allowlisted, read-only Figma seam: a bounded bridge to the real system of record — except the Backend Engineer's system of record is a running datastore, so its bridge is run, not just read.

08 — Tools & skills

Three layers: reach, verbs, know-how.

Integrations, tools, and skills are different things. Keeping them distinct is what lets a capability be composed, scoped per subagent, and reused across the workforce.

Integration

raw reach — the hands

A trust-scoped MCP / WebPlugin (§07): a datastore, a container runtime, a git host, an APM. Read on telemetry; run on ephemeral deps; gated on the PR and the prod migration.

Tool

composed verb — built on reach

A registered entry in the toolset, scoped per subagent by compute_minimum_toolset: run_command, apply_migrations, test_evidence. Mechanical and verifiable — not reasoning.

Skill

know-how — shapes how

Authored reference: a playbook the agent reads (zero-downtime-migrations). Not a callable verb. It's what stops a fluent model from being a green-tested, production-breaking fabricator.

Skills vs. the contract vs. memory

Three distinct things, cleanly split — the AGENTS.md · SKILL.md · contract layering. A skill is durable craft know-how ("how to make a migration backward-compatible"); the contract + data model is this service's specific shape + invariants; memory is contingent fact ("the payments table deadlocks under this lock order — order updates before reads"). The skill is portable; the contract is per-service; the memory is per-history.

09 — How "done" is decided

A reviewed build with a durable evidence floor.

A service's failure mode is mostly hidden below the unit-test line — unproven under load, unsafe, unmigratable — so the Backend Engineer's DoD leads with a deterministic evidence floor, exactly as the Frontend Engineer's does: a test_evidence/ bundle exists in the worktree, its manifest.json is all-green, and the kernel's verify command (build + unit + integration-on-real-DB + contract) exits 0. A service that passes its own mocks but has no bundle is not done.

Above the floor, correctness-in-the-real-world is a judgment against a running system, so "done" adds two verdicts, mirroring the Frontend's reviewed_build over an evidence-floor command:

In-beat · Verifier + Reviewer

The API-Verifier drove the running service (contract + property + real endpoints + health) and returned PASS; the read-only Code-Reviewer approved the diff (correct, tested, no regression, on-contract, secure, backward-compatible). Quality is enforced where the code is made.

Out-of-beat · the evidence floor

The kernel's verification oracle greps manifest.json deterministically: the bundle exists, every gate is green, coverage + mutation above floor, SLO thresholds not breached, security scan clean, migration round-trip passed. Ungameable; the review is calibrated to a senior eye.

Done means, in one beat — six checkable truths

  • Green build. The discovered verify command (build + unit/component + integration-on-real-DB + contract) exits 0.
  • Behaviour proven against the running service. The API-Verifier drove the live service and returned PASS against the acceptance criteria — including error paths and the auth boundary.
  • Measured, not assumed. Load SLOs (p95/p99 + error-rate) inside budget via exit-code gates; coverage + mutation score above floor; the security scan (BOLA, injection, secrets, deps) is clean.
  • Migration safe. Expand → migrate → contract ordering, with a passing forward→verify→rollback→verify round-trip against production-sized data — whenever the diff touches schema.
  • Evidence on disk. A test_evidence/ bundle landed in the worktree; the DoD's deterministic floor greps manifest.json. Not a placeholder file, not a line in a log.
  • Diff approved. The read-only Code-Reviewer approved (correct, tested, no regression, on-contract, backward-compatible, secure).

The quality bar — what "done" means beyond a green check

A build can pass its tests and still be a bad service. The engineer holds seven dimensions; the DoD makes each checkable so none is skipped and quietly "fixed later."

Correct

Does what the acceptance criteria say, across the states that actually occur — not just the happy path.

Secure

Every object authorized (BOLA), every query parameterized, every input validated, no secret hardcoded. Scan-clean.

Fast

Core SLOs inside budget under load. p95 ≤ 200ms p99 ≤ 500ms err < 1%

Resilient

Timeout / retry-with-jitter / circuit-breaker on every dependency; idempotent consumers; failure paths exercised.

Migratable

Expand-contract, backward-compatible, batched backfills, a tested rollback — applies while the old code still runs.

Observable

Health, metrics, and traces ship with the change; the SLIs it will be judged on are instrumented.

Maintainable

Smallest change, clear boundaries (hexagonal), tests that fail only for useful reasons.

Proven

Every one of the above resolves to a file in the evidence bundle — asserted nowhere, checked everywhere.

Anti-reward-hacking — the non-negotiable, from the field's failure data

Because an autonomous agent writes both the code and the tests, the DoD is designed so it cannot pass by cheating: the grader's tests are read-only / outside the workspace the agent can edit (SWE-bench's model); the brief explicitly forbids removing or editing tests; the Code-Reviewer diffs the touched test files; and the mutation score proves the tests would actually catch a bug rather than being toothless. A green suite the agent could have gamed is not evidence — a held-out one it couldn't is.

10 — The test_evidence layer

A durable, machine-readable bundle the beat emits — "it was tested" as a directory.

This is the Backend Engineer's signature layer — the analog of the Designer's DESIGN.md substrate and the Frontend's evidence bundle. It makes "proven, safe, operable" structural, because the proof is a set of files a DoD checker reads, not a sentence in a transcript. Each file is produced by a gate that already exited non-zero on failure, so the bundle's existence with all-green statuses is itself the proof.

# test_evidence/ — the durable proof bundle, one per beat
test_evidence/
  manifest.json            # index + top-level verdict + per-gate status (the DoD reads this alone)
  static/     typecheck.txt · lint.json · security-scan.sarif   # types, lint, SAST
  unit/       junit-unit.xml · coverage.xml                # JUnit + Cobertura
  integration/ junit-integration.xml · containers.log          # proof a REAL db was used
  api/        openapi.json · schemathesis-junit.xml · dredd-report.json
  contracts/  *.pact.json · provider-verification.json · can-i-deploy.json
  migrations/ applied.log · rollback-roundtrip.txt · data-assertions.json
  load/       k6-summary.json          # p95/p99, error-rate vs thresholds
  mutation/   stryker-report.json      # score vs break threshold — did the tests bite?
  smoke/      healthcheck.json         # /healthz + /readyz post-deploy
# manifest.json — the single file the DoD greps
{
  "commit": "…", "verdict": "pass",
  "gates": {
    "static":      { "status": "pass", "typecheck_errors": 0 },
    "unit":        { "status": "pass", "tests": 412, "failures": 0, "coverage_pct": 87.4 },
    "integration": { "status": "pass", "backend": "postgres:16 (testcontainers)", "failures": 0 },
    "api":         { "status": "pass", "checks": ["not_a_server_error","response_schema_conformance"] },
    "contracts":   { "status": "pass", "provider_verified": true, "can_i_deploy": true },
    "migrations":  { "status": "pass", "rollback_roundtrip": true },
    "load":        { "status": "pass", "p95_ms": 180, "p99_ms": 420, "error_rate": 0.003 },
    "mutation":    { "status": "pass", "score": 71.2, "break_threshold": 50 },

Tiers of self-failing gates

static → unit → integration-on-real-DB → contract → migration → load/SLO → mutation → smoke. Each exits non-zero on failure (k6 exits 99 on a threshold breach; Stryker exits non-zero below its break score), so the pipeline itself enforces the floor — the bundle can't be all-green unless every gate genuinely passed.

test_evidence — the deterministic collator

The chorus-native primitive (the Designer's design_lint, re-pointed): discovers the project's commands, runs each gate, collates the standard artifacts, and writes the bundle + manifest.json. The Verifier's authoritative signal and the DoD's grep target.

Standard, machine-parseable formats

JUnit XML (results) · Cobertura/LCOV (coverage) · SARIF (security) · Pact JSON + broker verification (contracts) · k6 summary JSON (load) · Stryker JSON (mutation). Every one is an industry standard a CI already renders — nothing bespoke to trust.

Real deps, not mocks — the credibility line

containers.log is deliberate: it proves the integration tests ran against a real Postgres/Redis, not H2 or a stub. The three things that make backend evidence credible: real dependencies, percentile SLOs as hard gates, and a mutation score.

The Backend Engineer's "confidently wrong"

The Analyst's failure is a fabricated metric; the Designer's is a plausible screen that's quietly broken; the Backend Engineer's is a plausible service that passes its own tests and falls over in production. The evidence bundle is the structural defence: the agent builds against a real system, and every claim of "it works" is a checkable file — run against a real DB, under load, across a migration, with the tests it could not edit. Proven and safe stop being a matter of the reviewer's trust and become a matter of record.

11 — The verification library (the golden references)

Prove against a proven method — don't invent a test strategy from a blank page.

§10 says the beat emits an evidence bundle. But which tests, in what shape, proving what? Hand-rolling a test strategy is exactly the blank-page task an LLM does worst — and the one where it most easily fools itself. The answer is the same as the Designer's DESIGN.md library: a curated set of proven verification methods, each with a canonical tool and a machine-checkable output, that the beat imitates rather than invents.

Test Honeycomb shapeIntegration-heavy for services: few isolated unit tests, a strong integration core, few integrated e2e — the shape most apt for backend (vs the UI Pyramid).Fowler / Spotify
Real-DB integrationSerialization + queries work against the same service type as production, not an in-memory fake.Testcontainers · JUnit XML + containers.log
Property-based API conformanceThe running service matches its OpenAPI spec across thousands of generated inputs — no 5xx on edge cases, responses conform to schema.Schemathesis · JUnit XML + curl repros
Consumer-driven contractsCross-service compatibility without a full e2e environment — the provider satisfies exactly what each consumer uses; can-i-deploy gates release.Pact · pact JSON + verification record
Migration round-tripThe schema change applies while the old code still runs, backfills correctly, and rolls back: forward→verify→rollback→verify, at production data volume.expand-contract · rollback-roundtrip.txt

Four ways it plugs into the Backend Engineer

new① Method seed

At hire, the discovered stack maps to its canonical methods — Postgres → Testcontainers, an OpenAPI service → Schemathesis + Pact, a schema change → expand-contract round-trip. The beat starts from a proven strategy instead of improvising one. The analog of the Designer's cold-start DESIGN.md seed.

new② Format exemplars

The standard artifact formats (JUnit / Cobertura / SARIF / Pact / k6 / Stryker) are worked examples of what a gate must emit. When test_evidence collates the bundle, these are the canonical shapes — so the output is machine-parseable evidence, not ad-hoc logs.

new③ Golden reference for the DoD + Reviewer

Each method's output is the ground truth the DoD greps and the Code-Reviewer reads: can-i-deploy: true, rollback_roundtrip: true, p99_ms < threshold. "Proven" becomes checkable against a concrete artifact, not a vibe.

new④ Eval & acceptance fixtures

"Add the idempotent endpoint and prove it with a Pact contract + a k6 SLO" is a self-contained, gradeable task with a paired evidence output — ideal fixtures for the DoD and for benchmarking the loop, the way SWE-bench Verified benchmarks a real patch.

Fork-not-invent — the reuse discipline, applied to proof
Just as the Designer starts from a battle-tested design system and diverges, the Backend Engineer starts from battle-tested verification methods and applies them — never hand-rolling a test philosophy per beat. The library is the proof-substrate equivalent of a skeleton project: adopt the canonical method for the stack, then run it. It closes the gap §10 leaves open — where a trustworthy test strategy comes from — and it is what keeps an autonomous agent from grading itself with tests it quietly declawed.

12 — Authority & governance

It builds and proves the service; it does not merge, own the schema of record, or run prod.

The Backend Engineer has broad read + run and a narrow, gated ship. It can read the contract, the codebase, and the deps; install, migrate, run, and load-test in its confined worktree; and open a proven PR. It cannot merge to production, alter the shared schema of record without the owner, or take a money-moving / data-destroying action.

CANBuild, run & prove

Implement to the contract; install deps + apply migrations in the worktree; run the service + real dependencies; drive load; author + run all gates; open a PR with evidence for review.

CANNOTMerge, own infra, or scope

No autonomous merge to prod, no unreviewed change to the shared schema of record, no destructive prod data op, no deciding the roadmap — that's the reviewer's, the DBA/owner's, the PM's, and the board's.

The hard boundary — three roles it is not

It is not the PM (who decides what to build — the Backend Engineer builds the how), not the Designer / Frontend Engineer (who own the experience and the interface — the Backend Engineer serves the data behind them), and not the platform / DevOps owner (who owns production infra and the schema of record — the Backend Engineer proposes a migration and a service, and hands off a reviewable PR). When a change alters a cross-service contract, the shared schema, or the reliability budget of another team, it escalates to the owner; a HumanApproval gate stands in front of anything that reaches production or moves money — the exact fail-closed seam the Marketer uses for go-live.

13 — Proactive voice

The crux — build vs. ask.

An engineer that asks about every ambiguity is slow; one that invents an answer to every gap ships a wrong contract. The contract + the acceptance criteria make the line principled: build when the contract covers the case; ask when it doesn't and the call is consequential or irreversible.

Build & proceed

The contract and acceptance criteria cover it, the invariants hold, the gates pass — build it and move. Most tickets are here. Flagging a reliability gap (a missing index the load test exposes, a slipping p99) is itself proactive: the engineer proposes the fix, it doesn't silently absorb the debt.

Escalate & ask

The contract genuinely doesn't cover it and guessing would set a precedent or be irreversible — a cross-service contract change, a shared-schema migration, a data-destroying step, a security trade-off. Surface the specific gap with two on-contract options; a one-line "the spec doesn't define X; here are two safe paths" beats a confident wrong migration.

15 — Tribal knowledge (memory)

What shipped, what broke, what the system learned the hard way.

Design decisions

The architectural calls and why — "we chose an outbox here because the write and the event must be atomic" — so a later service stays consistent with the pattern instead of re-deciding it.

Incidents — what broke

The deadlock from an inconsistent lock order, the migration that locked the table, the N+1 that melted the DB, the retry storm without jitter — accrued so the same failure isn't re-shipped. Maps to chorus project-scoped memory.

Performance baselines

The p95/p99 this endpoint holds today, the query plan it depends on, the throughput ceiling — so a regression is caught against a remembered number, not re-discovered in production.

Working memory

The in-beat scratchpad across a multi-step build — the migration state, what's been tried, the failing gate — cleared each beat. Maps to chorus working memory.

Memory keeps the system from re-breaking

The distinctive tier is incidents: the Backend Engineer doesn't just build the service, it remembers how the last one failed in production and designs against it — so reliability compounds instead of relearning the same outage. Continuity of the system's hard-won lessons, not of the employee.

16 — Build map

Net-new, but mostly a re-skin of the Engineer + the Frontend Engineer.

There is no chorus backend_engineer/ package yet. But the archetype is the Engineer's structural twin and the Frontend Engineer's mirror, so most layers are a re-point of proven machinery onto the "prove it against a real system" substrate — smallest-blast-radius first.

src/chorus_employee/backend_engineer/
  __init__.py         # backend_engineer_plugin() — the role triple + declared routines
  _brief.py           # prove-the-service brief (real deps, held-out grader, PR not merge)
  _harness.py         # build/run harness (run_command, git, http_request, test_evidence)
  _dod.py             # reviewed_build over a deterministic evidence-floor command
  _lander.py          # backend lander → opens the pr artifact (+ evidence bundle)
  _routines.py        # dependency/vuln scan + SLO/error-budget watch
  _subagents/         # test-author · api-verifier · code-reviewer (typed returns)
  skills/             # the backend-craft library (api, data, scale, testing, security)
src/chorus_tools/     # test_evidence tool (collator) + apply_migrations / start_service / http_request

Slices (mirror the Frontend Engineer's)

  1. Walking skeleton — manifest + brief + tools (read/write/run/git) + reviewed_build DoD. Implements and lands a PR that builds green. backend
  2. Tests-in-beat — the test_evidence primitive (registered unconditionally) + Test-Author subagent + the evidence-floor DoD. Every landed change carries proof. backend
  3. Real-system verification — health-gated docker-compose startup + Testcontainers integration + contract/property tests; the API-Verifier subagent + its typed ApiTestVerdict. backend
  4. Craft depth + operability — author the skill playbooks; the Code-Reviewer subagent; load/SLO gates + mutation baselines + migration round-trip + the security scan. deferred

Design decisions (redirect any of these)

  • Stack-agnostic by construction. No framework, language, or datastore is hardcoded — a brownfield beat probes the repo, detects the stack (Go+Postgres, Python+Mongo, Node+Redis, …), and binds to its discovered commands + libraries; a greenfield / cold-start beat decides the stack with reasons, scaffolds from a proven starter, and writes the probe surface future beats read. The loop, DoD, and evidence shape are invariant; only the bindings are data (§03).
  • The Backend Engineer ships a service, landed as a reviewable PR. Build and prove freely; merging to prod crosses the same fail-closed gate as the Marketer's go-live — no autonomous merge.
  • Governed against the unproven, unsafe, unmigratable service. A durable test_evidence bundle is the floor; real dependencies + a held-out grader make the proof credible; SLOs + mutation score keep it honest.
  • Proof is a first-class artifact. A machine-readable test_evidence/ bundle + manifest.json per beat — the field's converged discipline — not a claim in the transcript.
  • Correctness is proven against a real system. Integration against a real Postgres/Redis (Testcontainers), the running API under load — because a suite that passes on mocks proves the mocks.
  • Safe = confined, not narrow. UNRESTRICTED commands inside a registry-only egress allowlist, secrets stripped before the autonomous phase, worktree confinement.
  • Register test_evidence unconditionally. A pure worktree tool, never ledger-gated — the fix for the exact bug found on the Designer's design_lint.
  • It is not the PM, the Designer, or the platform owner. Builds the how (not the what), serves the data (not the experience), proposes the migration (doesn't own prod).
  • Mostly a re-skin. Engineer's sandbox + DoD, Frontend's evidence bundle + Verifier, pointed at a running datastore. Reuse over invention.
