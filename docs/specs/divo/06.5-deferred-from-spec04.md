# 06.5 — Deferred from spec 04 (post-spec-06 batch)

Spec 04 (*Outcomes, DoD & governance*) has five subsystems. Three are **shipped**; the rest
need building blocks that don't exist yet — chiefly the **roles/workforce** of spec 06 and one
**dream** capability (per-task permission policy). This doc is the single backlog of every
spec-04 item not yet implemented, to be picked up **after spec 06 lands**. It does not change any
design — it only records what's left, why it was deferred, and what unblocks it.

> Read alongside [04-outcomes-and-governance.md](04-outcomes-and-governance.md). Section numbers
> here mirror spec 04's (§1 DoD · §2 landing · §4 trust · §5 governance). §3 budgets is **done**
> and is omitted.

## What already shipped from spec 04

So this doc is read in context — these are *not* deferred:

- **§1 (partial).** Typed `Verifier` (`Command` / `AgentReview` / `HumanApproval`) + the 1:1 `dod`
  row, repo (`DodRepo.create` / `get_for_task` / `verifier_for_task` / `record_verdict`), and CLI
  (`dod set <task> command|agent_review|human_approval`). **Command-DoD enforcement** rides into
  dream as `run_task(verification_steps=…)` — the evaluator runs the shell command as a real

- **§3 budgets — fully done.** Two-gate hard-stop enforcer (`budgets/_enforcer.py`), live-recompute
  spend, cost-event pricing (model + token counts), CLI verbs, and tick integration. Nothing
  deferred.
- **§5 (partial).** The task-gate `GovernanceResolver` (acceptance + authorization gates), the
  `ApprovalGate` model, and CLI approval verbs (open / list / approve / deny). Budget-override

## §1 — DoD: what's left

| Item | Status | Unblocked by |
|---|---|---|
| `Command` enforcement via dream `verification_steps` | **done** | — |
| HumanApproval beat-hook → §5 acceptance gate | **done** | — |
| Self-repair ladder rungs 1 / 3 / 4 | **done** | — |
| **AgentReview enforcement** (judgment gate) | deferred | **spec 06** (Reviewer role) |
| **Ladder rung 2** (reviewer escalation → `in_review`) | deferred | **spec 06** (Reviewer role) |
| **DoD auto-generation at intake** (`dod_generator`) | deferred | **spec 06** (role plugins wired into intake) |
| **DoD revisability** (tighten / loosen, `dod.revision`) | deferred | self-contained core; manager-authority via **spec 06** |

**AgentReview + rung 2.** A judgment-class DoD ("a Reviewer employee renders a verdict") is just
self-report until a **Reviewer role** exists to render it (spec 04 §1: *"judgment-class work without
a Reviewer is just self-report… the Reviewer role ships with the first non-code role"*). Today
`Verifier.agent_review()` round-trips through the ledger and `verification_steps()` correctly yields
`()` (no objective subprocess), but nothing routes an `in_review` task to a reviewer or records the
verdict back onto the `dod` row. Build after spec 06 defines the Reviewer role + the `in_review`
hand-off path. Rung 2 of the escalation ladder (repair budget exhausted, judgment-class → open an
`in_review` path to the Reviewer) lands together with it.

**DoD auto-generation at intake.** Spec 04 §1 *"Who generates the DoD"*: the DoD is generated by the
**assignee's role plugin** (`dod_generator`, spec 06 §2) at intake/decomposition — the role knows its
artifact class, so an Engineer task auto-gets a `Command` gate, a PM task an `AgentReview` gate.
Today `dod_generator` is *defined* on the `Role` plugin but **never called** — DoDs are only set
manually (CLI / ledger). Wiring intake to call the assignee role's `dod_generator` (and, for a
decomposed child, the decomposing manager's role) needs roles bound to assignment, which is spec 06.

**DoD revisability.** Spec 04 §1 *"Revisability"*: the `dod` row is mutable only through a typed,
audited path (`dod.revision` bump) — a **tightening** revision (manager adds a check) is allowed
mid-task and emits a `decomposed`-class audit row; a **loosening** revision (remove/relax) requires
the *same* approval the artifact class demands and lands as an `approval(subject_kind='task')`; a
revision while a beat is in flight takes effect on the **next** disposition (never retro-passes the
running evaluator). The pure ledger mechanics (a revisioned `dod`, the in-force-at-evaluation rule)
are self-contained, but "the assignee's manager" / artifact-class authority is a spec-06 role
concept, so the whole item batches here.

## §2 — Outcome landing: what's left

The model exists; **every behaviour is deferred.** "Done" must mean the deliverable *landed
somewhere a reviewer can verify it* — today nothing calls `land()`, so a passed beat records no
artifact.

| Item | Status | Unblocked by |
|---|---|---|
| `Artifact` / `ArtifactType` model + repos | **done** | — |
| `OutcomeLander` protocol (the seam) | **done** | — |
| **Concrete role landers** (Engineer / Reviewer / PM / Analyst) | deferred | **spec 06** (roles) |
| **Kernel calls `land()`** after a passed beat | deferred | needs a concrete lander per role |
| **Server-canonicalized artifact metadata** (`content_type`, `byte_size`, paths) | deferred | with the concrete landers |
| **`workspace_file` reference safety** (relative-only, no `..`, no host-absolute) | deferred | with the concrete landers |
| **Strict completion pattern** (verify → persist → link in final comment → set status) | deferred | with the concrete landers |

Each landing is **role-specific** (spec 04 §2 table): Engineer = PR → CI green → merge; Reviewer = an
approve/block verdict; PM = a persisted spec/decision; Analyst = a persisted finding. None of these
roles exist before spec 06, so the landers and the kernel `land()` call that drives them batch here.
The two safety rules — server (not worker) canonicalizes blob metadata, and `workspace_file` is a
second-class relative pointer with no `..` escape and no host-absolute path — are implemented *with*
the landers, since they only matter once an artifact is actually persisted.

## §4 — Trust (fail-closed presets): what's left

**Entirely deferred.** Nothing in §4 is built. It is batched into this post-spec-06 round per the
decision to do all remaining spec-04 work together, even though §4's blocker is **dream**, not spec 06.

| Item | Status | Unblocked by |
|---|---|---|
| `TrustPreset` model (`standard` / `low_trust_review`) | deferred | self-contained |
| **Fail-closed layered resolution** (intersect employee/task/run; narrower wins) | deferred | self-contained |
| Boundary scope (task-in-boundary, secret-ref allow-list, no inline secrets) | deferred | self-contained |
| **Resolved preset → dream `permissions` Policy + `sandbox` + role toolset** (per beat) | deferred | **dream** (per-task policy) |

**The pure-chorus core is self-contained.** The preset value object and the fail-closed resolution
rule (spec 04 §4: *"intersect the layered policy sources (employee / task / run); narrower wins; any
conflict, cross-scope, or unsupported preset → denied; a low-trust preset with no concrete scope is
denied"*) depend on nothing external — they can be built and unit-tested in chorus alone.

**Enforcement needs a dream change.** dream's trust is **per-harness** (`build_harness(permission_mode=…)`);
`run_task` takes **no per-task policy override**. So applying a *task's* resolved preset to its beat
requires either (a) a dream change giving `run_task` a per-task policy/permission argument, or
(b) chorus maintaining one harness per preset and routing each beat to the matching harness. That
choice is the first design question when this item is picked up. The mechanism it maps onto already
exists in dream (the 9-step fail-closed `permissions.evaluate`, the `sandbox` adapter, the `roles`
toolset) — chorus only supplies the preset resolution + the boundary scope + the wiring.

The invariant to preserve (spec 04 §4): **containment ≠ privacy.** A low-trust preset limits what the
agent can read/mutate via the API and stops raw untrusted output from being promoted into
higher-trust context — it must **not** hide work from the board.

## §5 — Governance: what's left

| Item | Status | Unblocked by |
|---|---|---|
| Task-gate resolver (acceptance / authorization) + CLI | **done** | — |
| `budget_override` approvals (via §3) | **done** | — |
| **`hire_employee`** governed action | deferred | **spec 06** (employee lifecycle, `pending` state) |
| **`plan_approval`** (approve a manager's decomposed plan) | deferred | **spec 02 §4** decomposition + **spec 06** |
| **`board_approval`** distinct flow | deferred | **spec 06** |
| **`revision_requested`** approval status | deferred | self-contained (small) |

**`hire_employee`.** Spec 04 §5: *"approving a `hire_employee` activates the pending employee +
upserts its budget policy; rejecting terminates it."* This needs an employee that can be **pending**
(a workforce lifecycle state that doesn't exist yet) and the activate/terminate transitions — all
spec 06.

**`plan_approval` / `board_approval`.** `plan_approval` couples to spec 02 §4 decomposition (you
approve a *plan revision*); `board_approval` is a distinct governed flow. Both wait on the
roles/manager hierarchy of spec 06.

**`revision_requested` status.** The `approval.status` FSM in spec 04 §5 is
`pending → approved | rejected | revision_requested`. Today `ApprovalStatus` has no
`revision_requested` member and the resolver only handles approve/deny. This is self-contained (a
ledger enum value + a resolver branch) but batches here because its only consumers
(`plan_approval` / DoD-loosening revisions) are themselves deferred.

## Build order when this batch is picked up

Spec 06 (roles/workforce) is the gate for most of it. A sensible sequence once it lands:

1. **§1 DoD auto-generation** — call the assignee role's `dod_generator` at intake (smallest, unblocks realistic DoDs everywhere).
2. **§2 landers + kernel `land()`** — Engineer lander first (PR/CI), then Reviewer/PM/Analyst; with metadata canonicalization + `workspace_file` safety.
3. **§1 AgentReview + ladder rung 2** — route `in_review` to the Reviewer role, record the verdict.
4. **§5 `hire_employee`** (needs the employee `pending` state) → then `plan_approval` / `board_approval` + `revision_requested`.
5. **§1 DoD revisability** — the revisioned `dod` + tighten/loosen authority.
6. **§4 trust** — preset model + fail-closed resolution (chorus-only) first; then the dream wiring once the per-task-policy decision is made.

Items 1–5 are chorus-only once spec 06 exists. Item 6's enforcement half is the only piece that also
needs a dream change.
