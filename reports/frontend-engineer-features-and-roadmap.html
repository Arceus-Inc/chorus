Chorus · Frontend Engineer (Finn)

Features & Roadmap

Part 1 documents what Finn is today — an autonomous, framework-agnostic Frontend Engineer employee that reads an intent, chooses its own stack, builds a working app, and proves it works with real tests. Part 2 proposes advanced features that would deepen that "prove it works" identity and broaden what Finn can take on.

Part 1

What Finn is today

Finn is a build role, not a spec role: it runs commands, scaffolds a project, writes and executes tests in a real browser, and iterates red→green inside an isolated git worktree. Its defining principle is evidence — nothing is "done" until the tests have actually run and the output is captured.

Framework-agnostic by construction

◇The engineer chooses the stack

No framework is named anywhere in the Python code or the brief. Finn reads the intent + any existing code, loads choosing-a-frontend-stack, and decides: hand-written HTML/JS, a component framework (React/Vue/Svelte), or a meta-framework. Validated live — for the storefront task it independently chose React + TypeScript + Vite + Playwright and passed every gate.

▤Neutral brief & DoD

The brief describes outcomes (a working, accessible, tested app) and a pure/view seam — never a library. The Definition-of-Done floor checks stack-agnostic markers: a package.json with a "test" script, a playwright.config.*, captured unit + e2e logs, and a ≥150-word summary that must record the stack decision and the test results.

Prove-it-works machinery

⌘Real command execution

run_command + git in an UNRESTRICTED sandbox, confined to an isolated worktree. Finn installs deps, scaffolds, runs a dev/preview server, and drives Node, npm, and npx playwright for itself — an autonomous build loop, not a suggestion engine.

🔎test_evidence scanner

A deterministic, read-only tool that scans the worktree and reports exactly what proof exists or is missing (project manifest, e2e harness, unit log, e2e log, summary) with typed findings like unit_not_run or thin_summary. Finn self-checks it before declaring done; the DoD floor re-checks it after.

↻Independent re-verification

After the beat, the harness re-runs npm test and npx playwright test itself with CI=1 in the shipped worktree — so a "pass" means the code went green again under the harness's own hands, not just Finn's self-report.

▦Per-task flow reports

Each run emits a self-contained HTML flow report: the phase-by-phase tool timeline, subagent activity, sprint evaluations, the independent re-verification verdict, and the produced artifacts — a readable audit trail of how the app was built.

In-beat quality pressure — two read-only subagents

✓Code-Reviewer

Reads package.json + source and reviews correctness, accessibility, and test integrity through a MISFIT-STACK lens — flagging both over-engineering (a framework where vanilla would do) and under-engineering. Read-only (read_file / working_memory_read / test_evidence), so Finn keeps ownership of fixes.

◉UI-Tester

Audits the proof: does the e2e genuinely drive the real UI and assert real behaviour, or is it hollow? Guards against tests that pass without testing anything. Also read-only.

Part 2

Proposed advanced features

Finn's identity is "prove it works." The highest-leverage additions widen what "works" is machine-checked to mean — accessibility, visuals, performance, and security — and then broaden the stacks and workflows Finn can take on. Each proposal notes how it plugs into the existing harness (a new skill, a DoD signal, a subagent, or an MCP), so none of it is a rewrite.

Theme A · Deepen the proof (highest leverage)
1

Automated accessibility auditing (axe-core)

Finn already authors accessibly (semantic HTML, focus, contrast skills) but never machine-verifies it. Wire @axe-core/playwright into the e2e to run a WCAG scan on each key view, and add an a11y DoD signal that fails on serious/critical violations. Closes the loop between the three a11y skills and actual evidence.

Priority 1Plugs in as: a new accessibility-auditing skill + a test_evidence finding + an optional a11y-auditor subagent.
2

Visual-regression / screenshot-diff testing

DOM assertions miss visual breakage (layout, overflow, contrast, dark-mode). Adopt Playwright's toHaveScreenshot() with committed baselines so unintended visual changes fail the e2e. Especially valuable once Finn iterates on an existing app across beats.

Priority 1Plugs in as: a visual-regression skill + baseline artifacts in the evidence bundle.
3

Performance & bundle-size budgets

Run Lighthouse (or an equivalent) against the preview build for perf/best-practice scores, and add a bundle-size budget (Finn already emits a known build size — ~240 kB / 76 kB gzip for the storefront). Fail when a budget is exceeded, so quality doesn't silently regress.

Priority 2Plugs in as: a performance-budgets skill + a DoD signal reading the build report.
4

Explicit type-strictness & dependency-security gates

Make tsc --noEmit (strict) an explicit DoD signal rather than an implicit build side-effect, and run npm audit (or a supply-chain check) so Finn refuses to ship with high-severity advisories. Cheap, high-trust guardrails.

Priority 2Plugs in as: two test_evidence findings (types_not_checked, vulnerable_deps).
Theme B · Broaden the stacks & decisions
5

Framework doctor skills for Vue, Svelte, SolidJS & Angular

Today react-doctor is the only deep framework playbook, so choosing-a-frontend-stack can genuinely pick React but is thinner behind the other options. Author matching doctor skills (reactivity/stores for Svelte & Solid, composition API for Vue, signals/DI for Angular) so every choice has real depth behind it.

Priority 1Plugs in as: new on-demand skills — no Python change (the whole point of the agnostic design).
6

A "framework-fit scorer"

An up-front decision aid that scores the chosen stack against the task shape (does the intent justify a meta-framework? is a state library overkill for three views?). Complements the Code-Reviewer's after-the-fact MISFIT-STACK lens by catching a poor fit before the build.

Priority 3Plugs in as: a skill section in choosing-a-frontend-stack, or a lightweight pre-build subagent.
7

Incremental building on an existing repo

Finn currently shines at greenfield scaffolds. Add a mode that reads an existing codebase's conventions (stack, structure, test setup) and extends it across beats — matching the house style instead of imposing a new one. This is what most real frontend work actually is.

Priority 2Plugs in as: a working-in-an-existing-app skill + a "detect, don't scaffold" branch in the brief.
Theme C · Delivery & richer inputs
8

Enable Playwright MCP for interactive UI driving

Turn on the deferred mcp for exploratory debugging and self-healing selector discovery — letting Finn open the running app, inspect the accessibility tree, and find robust locators before writing the deterministic spec. The committed e2e stays the gate; MCP is the scouting tool.

Shipped ✓Delivered as: a role-declared mcp_servers field on the manifest → .harness/mcp-allowlist.toml at materialize, with mcp=True. Verified end-to-end: connects on Windows (SDK resolves npx→npx.cmd), advertises 23 browser tools, and drives a real browser (navigate + snapshot).
9

CI workflow generation

Emit a GitHub Actions (or equivalent) workflow that runs the exact build + unit + e2e gates Finn ran locally — so the proof reproduces in CI on every push, not just once at build time. Makes Finn's evidence durable for the team, not just the beat.

Priority 3Plugs in as: a ci-workflow-authoring skill emitting a .github/workflows file into the worktree.
10

Component stories & design-token adherence

Generate Storybook stories for built components (isolated review + a visual catalog that pairs with proposal #2), and — when a Designer handoff supplies a design system — lint that the app uses design tokens rather than magic values. Tightens the Designer→Engineer seam already present in Chorus.

Priority 3Plugs in as: a component-stories skill + a design-token-adherence check keyed off the handed-off system.
11

Screenshot-to-code (multimodal input)

Accept a design image as the intent and reproduce it, then verify with a visual diff against the input (reusing #2's machinery). Turns "here's a mockup" into a tested, working app — a natural capstone once visual-regression and the Designer seam are in place.

Priority 3Plugs in as: a multimodal intent path + a visual-diff acceptance gate.

Suggested sequencing

Do the Priority 1 items first — they close the biggest gap (Finn authors for a11y/visuals but doesn't yet machine-verify them) and add framework depth without touching Python. Priority 2 broadens trust (perf/type/security budgets, existing-repo mode); interactive Playwright MCP (item #8) is already Shipped. Priority 3 is delivery polish and richer inputs (CI, stories/tokens, screenshot-to-code). Every item lands as a skill, a DoD signal, a subagent, or an MCP flip — the framework-agnostic core stays intact.
